Title: Add a screen-reader-friendly Codex TUI mode
URL: https://github.com/openai/codex/issues/20489
Description: Body: I know external contributions may not be open right now, but I have a local fix ready if the team wants it or wants to use it as a reference.

VoiceOver users currently hear decorative terminal UI as content while Codex is working. For example, active command/status rows can be announced as repeated spaces, bullets, "running", and box-drawing characters. This interrupts reading code and makes it hard to review terminal output while Codex is still producing updates.

The main pain points:

- Live command/status rows are re-rendered with spinner/bullet/shimmer-style decoration.
- Box drawing such as `│` and `└` is announced as "box drawing".
- When new content arrives, VoiceOver may re-read older completed transcript content, causing the user to lose their place.

Recommended behavior:

- Add `codex --screen-reader` or `codex --accessible`.
- Disable spinner/shimmer/decorative bullets in that mode.
- Render plain indentation instead of box drawing.
- Minimize redraws that cause completed history to be treated as new spoken content.
- Keep the current visual TUI unchanged for users who want it.

I have a branch with a first patch that starts by making the no-animation path quieter for active exec/status rows and removing box drawing from exec output prefixes.

User: Engccer
Message: I would like to add the following concrete requirements to this request for an explicit, persistent screen-reader accessibility mode in Codex CLI.

Tables in assistant responses are difficult to navigate with a screen reader. Interactive choices and decorative output also make it harder to read and operate the CLI efficiently. Please provide a mode that covers both assistant response formatting and terminal interaction:

1. **Linear response formatting:** Prefer labeled lists or plain text instead of tables. When presenting tabular information, preserve the relationships between labels and values in a format that can be read sequentially.
2. **Explicit numbered selection:** For prompts with choices, announce each option with a number and allow the user to type that number and press Enter to select it. This should work for approval prompts, clarification questions, and CLI menus without requiring visual tracking of a highlighted row. Clearly announce the selected option and validation errors.
3. **No blank layout rows:** Remove empty lines used for decorative spacing in the accessible transcript and menus. Preserve meaningful whitespace inside code and preformatted content.
4. **No Astra sparkle effects:** Disable Astra stars/sparkles, shimmer effects, spinners, and other decorative animation in this mode. The Astra decoration is also discussed in #44561. Convey working, waiting for input, and completed states through stable, readable text.
5. **Complete keyboard access to history:** Make all earlier prompts, responses, tool output, and choices available for review with the keyboard and a screen reader, including content outside the current viewport. Provide predictable navigation and preserve the user's reading position when new output arrives.

Please expose this as a discoverable mode that can be enabled explicitly and saved in configuration. Screen-reader detection and `tui.animations = false` are useful starting points, but the requested mode also needs to address response structure, selection controls, spacing, and transcript navigation. Individual settings should remain adjustable to accommodate different speech and Braille workflows.

Current environment: Codex CLI 0.159.3 on Windows. These are requested accessibility behaviors, not a claim that every individual behavior above has been independently tested as a regression in this version.

User: Engccer
Message: Following up on [my earlier macOS VoiceOver report](https://github.com/openai/codex/issues/20489#issuecomment-6047206014): I have now confirmed a working workaround in actual screen-reader use.

Environment: Codex CLI 0.164.0, macOS 27.0.1, Apple Terminal, VoiceOver.

Previously, VoiceOver could access only the last visible portion of the conversation. After resuming the same conversation with `--no-alt-screen`, I could read all of the conversation history in that session. This is a user-tested result, not just an inference from configuration or source code. Animations were already disabled before this test.

Please make the behavior of `--no-alt-screen` the default when the proposed explicit screen-reader mode is enabled. Its persistent configuration equivalent is:

```toml
[tui]
alternate_screen = "never"
```

Users should not have to discover a separate terminal-rendering flag to access earlier messages. Please keep this setting individually adjustable for different screen-reader and Braille workflows.

This resolves the history-access problem in my tested macOS setup; it does not establish that every accessibility issue is resolved. I am also enabling this preference on Windows, but have not yet verified the Windows screen-reader behavior. The broader requests for linear response formatting, numbered selection, and stable reading position still stand.
